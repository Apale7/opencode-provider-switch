# 配置引用完整性与用户体验瑕疵梳理

## Summary

全面审计 opencode-provider-switch 配置模型中所有实体间的交叉引用关系，消除 CRUD 操作产生的悬空引用（dangling references），统一各边界的校验规则与错误反馈 UX。核心目标是：**删除任何一个实体后，系统不应产生不可恢复的运行时错误**。

## Problem

### 已知问题

1. **Provider 删除 → Alias target 悬空**：删除 provider 后，alias 中指向该 provider 的 target 不会被自动清除，后续代理请求匹配到该 target 时报错。
2. **Request Rewrite 规则悬空**：请求改写规则中引用 provider/alias/model，删除被引用实体后规则失效但无提示。
3. **同类引用型配置**：ProviderPriority、API Key scope（provider/alias 白名单）、Circuit Breaker 状态等可能存在同类悬空引用问题。

### 根因

- 配置模型采用 JSON 文件持久化，实体间通过 ID/Name 弱引用，无外键约束。
- 删除操作缺少级联清理或引用完整性校验。
- 不同边界（API save、CLI、Wails、import）的校验规则不统一。
- 悬空引用导致的运行时错误对用户不友好（500 而非明确提示）。

## Goals

1. **引用图全量审计**：穷举所有配置实体类型及其交叉引用关系，标注引用强弱与安全容忍度。
2. **删除级联一致性**：删除任意实体时，所有入向引用被清理（自动 alias target）或明确警告（手动 alias target）。
3. **保存时校验**：Config save 时拒绝创建指向不存在实体的引用（API Key scope、request rewrite rules 等）。
4. **运行时降级**：Proxy 遇到悬空引用时优雅降级（跳过不可用 target）而非报 500。
5. **UX 反馈统一**：UI/API/日志中悬空引用警告的呈现方式一致，提供可操作的修复指引。
6. **导入/同步安全**：Config 导入和 OpenCode sync 输出时校验引用完整性。

## Non-Goals

1. 不引入数据库或外键约束（保持 JSON config 文件）。
2. 不改变现有实体 ID 生成规则（Provider ID 仍为用户自定义字符串）。
3. 不改变协议匹配逻辑和路由语义。
4. 不新增功能实体，仅修复引用完整性。

## 调研维度（3 个互相独立子题）

### 子题 A：实体引用图审计（Entity Reference Graph Audit）

**目标**：穷举所有配置实体类型及其交叉引用，建立完整的引用关系矩阵。

**调研内容**：
- 枚举所有实体：Provider、Alias、Target、API Key、Request Rewrite Rule、Circuit Breaker State、ProviderPriority、Server Config
- 标注每个引用字段的：
  - 引用类型（ID 引用 / Name 引用 / Model 名称引用）
  - 引用强度（强引用：缺失则功能不可用 / 弱引用：缺失可降级）
  - 是否单向（被引用方无反向索引）
- 产出引用关系矩阵表，作为后续所有校验逻辑的权威依据

**产出物**：引用关系矩阵文档（嵌入设计文档）

### 子题 B：CRUD 生命周期完整性（CRUD Lifecycle Integrity）

**目标**：为每种实体的 Create / Update / Delete 操作定义引用完整性契约。

**调研内容**：
- **Delete 级联规则**：删除实体 X 时，哪些引用需要自动清理、哪些需要阻止删除、哪些需要警告用户
- **Update/Rename 影响面**：Provider ID 变更时，所有引用方的更新策略（级联更新 vs 禁止重命名）
- **Create 校验规则**：新建实体时，其引用的外部 ID/Name 是否在保存时校验存在性
- **Refresh/Discover 一致性**：Provider 模型刷新后，Target.Model 引用的模型名是否仍存在于 provider 的 Models 列表中

**关键场景矩阵**：

| 操作 | Provider | Alias | API Key | Rewrite Rule |
|------|----------|-------|---------|-------------|
| Delete → Alias.Target | **自动清理** auto target / **警告** manual target | — | — | — |
| Delete → ProviderPriority | **自动移除** | — | — | — |
| Delete → API Key scope | — | **自动移除** alias | — | — |
| Delete → Rewrite Rule | — | — | — | — |
| Update ID | **阻止或级联更新** | — | **级联更新** scope | **级联更新** |

### 子题 C：UX 反馈一致性（UX Feedback Consistency）

**目标**：统一所有边界上悬空引用的检测、展示与修复体验。

**调研内容**：
- **各边界校验一致性**：
  - Config Save API（Wails bridge）
  - HTTP REST API（web admin）
  - CLI（tui 配置工具）
  - Config 文件导入
  - OpenCode sync 输出
- **运行时降级策略**：
  - Proxy 路由遇到悬空 target：跳过并记录 warning vs 直接报错
  - `/models` 端点：隐藏不可用 alias vs 返回并标记
- **UI 警告呈现**：
  - Toast vs Banner vs Inline warning vs 详情页标记
  - 是否需要 "Fix for me" 一键修复按钮
  - 日志结构化字段（如 `dangling_ref=true`、`ref_type=provider`）
- **用户操作阻断策略**：
  - 保存时：拒绝 vs 警告但允许保存
  - 运行时：降级 vs 报错

## 容易遗漏的引用关系 / 场景

1. **反向引用无索引**：Alias.Target → Provider 是单向引用。Provider 自身不记录 "被哪些 alias 引用"，删除 provider 时需要全量扫描 alias 列表做清理——性能与正确性都依赖遍历完整性。
2. **Model 名称引用**：Target.Model 引用 provider.Models 中的模型名。Provider 模型刷新后，若某模型被移除，target 仍保留旧模型名——请求发送到 provider 时才会报 "model not found"。
3. **传递性悬空**：API Key scope → Alias → Target → 已删除 Provider。Alias 仍存在但所有 target 均不可用，API Key 的 alias scope 在形式上仍有效但实质上已空。
4. **Protocol 不匹配**：Alias 有 Protocol 字段，Target.Provider 的 Protocol 可能与之不一致（provider 协议变更后），但当前无校验。
5. **Circuit Breaker 内存状态**：熔断器在内存中维护 provider 状态，provider 删除后内存状态未同步清理，可能影响后续同名新 provider。
6. **ProviderPriority 孤儿**：优先级列表中包含已删除的 provider ID，导致排序异常或日志噪音。
7. **Request Rewrite Rules**：规则中引用 provider/alias/model 名称，被引用实体删除后规则静默失效，请求改写不生效且无提示。
8. **Config 导入 / 合并**：从外部导入的 config 文件可能包含对当前实例不存在实体的引用，导入时应校验。
9. **OpenCode Sync 输出**：sync 生成的配置可能引用已删除的 provider，下发到客户端后产生远程悬空引用。
10. **API Key scope 交集为空**：同时配置 provider 白名单和 alias 白名单，两者取交集后可能导致某 alias 无可用 target——用户可能在保存时看不到此后果。
11. **Default/fallback 引用**：系统级默认值中可能硬编码了 provider 或 model 名称引用。
12. **部分加载容错**：Config 文件若被外部修改导致部分实体缺失，系统加载时应报告所有悬空引用而非逐个失败。

## 依赖关系

```
auto-alias-simplify (07-21) ───┐
                                ├──→ config-ref-integrity (本任务)
provider-multi-ak (05-16) ─────┘
```

- **强依赖** `auto-alias-simplify`：该任务引入 `RemoveProviderAutoTargets()`（首个级联清理机制）、`AutoGenerated`/`Locked` 字段（决定清理策略）、`ProviderPriority`（新增引用关系）。本任务的审计范围需覆盖这些新增机制。
- **强依赖** `provider-multi-ak`：该任务引入 API Key → Provider/Alias 的 scope 引用。本任务需审计 API Key 删除级联和 scope 校验。
- **执行时序建议**：research（brainstorm + 调研）可与上述两任务并行，但 implement 必须在两者完成后执行，以审计完整引用图。
- **向后依赖**：本任务完成后，未来新增任何引用型字段都应在 `Remove*` 级联和 save 校验中注册。

## 优先级

| 优先级 | 事项 | 理由 |
|--------|------|------|
| **P0** | Provider 删除 → Alias target 自动清理（auto target） | 已知 bug，运行时 500 |
| **P0** | Provider 删除 → ProviderPriority 自动移除 | 数组残留，日志噪音 |
| **P1** | Config Save 时校验所有跨实体引用存在性 | 在源头阻止悬空引用产生 |
| **P1** | UI 中展示悬空引用警告 + 修复入口 | 用户可见的修复路径 |
| **P1** | API Key scope 引用校验（provider/alias ID 存在性） | 与 multi-ak 任务直接相关 |
| **P2** | Proxy 运行时对悬空 target 优雅降级（跳过而非 500） | 防御性兜底 |
| **P2** | Model 名称 staleness 检测（provider 刷新后） | 降低 "model not found" 错误 |
| **P2** | Request Rewrite Rule 引用校验 | 静默失效，用户无感知 |
| **P2** | Circuit Breaker 状态清理 | 内存泄漏 + 状态污染 |
| **P3** | Config 导入/导出引用完整性校验 | 运维场景，低频 |
| **P3** | 引用健康检查 CLI 命令 / API | 高级用户自助诊断 |
| **P3** | Protocol 不匹配警告 | 边界场景 |

## 验收关注点

### 功能性
1. 删除任何实体后，不存在指向该实体的**未被处理的引用**（已清理或已警告）
2. Config Save（所有入口：Wails/HTTP/CLI/Import）拒绝创建指向不存在实体的引用
3. 自动 alias target 删除时级联清理；手动 alias target 删除时保留但给出明确警告
4. Proxy 运行时遇到悬空 target 时返回结构化错误（含 `dangling_ref` 标记）而非裸 500

### 一致性
5. 同一引用完整性规则在 Wails、HTTP、CLI、Import 四个边界行为一致
6. 日志中所有悬空引用警告使用统一结构化字段（`dangling_ref`、`ref_type`、`ref_target`）
7. UI 中所有类型悬空引用使用同一警告组件（样式、交互、修复入口一致）

### 可观测性
8. 系统启动时自动扫描 config 并报告所有悬空引用（日志 + UI banner）
9. `/health` 或诊断 API 返回引用完整性状态

### 向后兼容
10. 旧配置文件中的悬空引用在加载时不阻塞启动，仅输出 warning
11. 不改变现有合法配置的保存格式和路由行为
