# Multiple provider API keys and access policies

## Summary

This task adds first-class API key management for the GUI and server web UI. Users can create multiple access keys, assign expiration and usage policy metadata, and restrict each key to a subset of providers and aliases.

The proxy must enforce key policy for OpenAI-compatible requests. `/models` must return only models visible to the calling key. Version text in the GUI/web shell must show the real app version instead of `dev`.

## Problem

Current configuration has one proxy-level API key shape and no UI dedicated to key lifecycle management. Operators cannot safely hand out scoped keys to different clients because all keys share the same provider/alias visibility and there is no expiration or quota metadata.

The GUI/web header also shows `dev` in places where packaged builds should show the effective version.

## Goals

- Show the correct runtime version in the GUI and browser web UI header.
- Add an API key configuration page that works in Wails desktop and HTTP browser fallback.
- Support multiple API keys with stable IDs, display names, enabled state, and secret masking.
- Support expiration policy:
  - never expires
  - fixed timestamp
  - relative duration from now, stored as an absolute expiration timestamp after save
- Support quota policy metadata:
  - token limit, enforceable with existing usage data where feasible
  - price limit interface reserved for future billing support, not enforced yet
- Support provider and alias visibility policy:
  - provider restrictions are transparent to API consumers
  - alias restrictions directly hide aliases from the key
  - `/models` response is reduced based on the key policy
  - if a provider is restricted and an alias has no remaining routable target, hide that alias
  - if an alias is restricted, hide that alias even when provider targets remain
- Keep all new user-visible UI copy i18n-ready for English and zh-CN.

## Non-Goals

1. Do not implement real price accounting in this task.
2. Do not add a database; keep current config-file persistence model.
3. Do not redesign provider/alias routing semantics except filtering by key policy.
4. Do not expose provider restrictions to API key callers.
5. Do not rotate or hash legacy secrets beyond the current config safety level unless required by existing patterns.
6. Do not change OpenCode sync output format unless existing proxy auth config requires a compatible update.

## UX Design

### Navigation

Add a top-level `API Keys` / `API 密钥` page to the existing left navigation. It belongs near Providers and Aliases because it controls who can use those routes.

### Page Layout

Use the same split-pane pattern as provider/alias management:

- Left pane: key list with status, expiration summary, quota summary, and visibility summary.
- Right pane: selected key detail form and policy controls.
- Empty state: explain that keys grant proxy access and can be scoped before sharing.

### Key Form

Fields:

- Name: human label, required.
- Enabled: toggle.
- Secret: generated by backend for new keys; masked after save; allow rotate/regenerate with confirmation.
- Expiration: segmented choices `Never`, `Fixed time`, `Relative days`.
- Token limit: optional positive integer.
- Price limit: optional number and currency placeholder, disabled or marked as reserved.
- Provider scope: all providers or selected providers.
- Alias scope: all aliases or selected aliases.

### Policy Feedback

Show derived visibility before save when possible:

- visible alias count
- hidden by provider restriction count
- hidden by alias restriction count
- warnings when the policy would expose zero aliases

### Secret Safety

After creation or rotation, show the plaintext secret once with copy action. After closing, show only masked value. Existing keys should never echo plaintext from config reads.

## Cross-Layer Contract

### Config

Add an `apiKeys` collection to the existing config model. Each entry stores:

- `id`: stable config ID
- `name`: display name
- `key`: secret value or current project-compatible secret storage field
- `disabled`: bool
- `expiresAt`: optional RFC3339 timestamp
- `tokenLimit`: optional integer
- `priceLimit`: optional object reserved for future billing, shape `{ "amount": number, "currency": string }`
- `providers`: optional allow-list; empty means all providers
- `aliases`: optional allow-list; empty means all aliases

Compatibility rules:

- Only legacy `server.api_key`: keep current behavior; treat it as an unrestricted admin proxy key.
- Only `apiKeys`: require one enabled, unexpired key from the collection.
- Both legacy `server.api_key` and `apiKeys`: legacy key remains unrestricted for compatibility; collection keys use their own policy.
- Empty legacy key and empty `apiKeys`: keep existing no-auth behavior only for local/dev configs where `server.api_key` is empty; do not create implicit scoped keys.
- Existing configs that omit `server.api_key` and are loaded through current defaults keep the current `DefaultLocalAPIKey` behavior. Implementations should not infer no-auth from an omitted field after defaulting.
- Explicit empty `server.api_key` means no legacy key. If no `apiKeys` exist, preserve current no-auth behavior for compatibility; do not silently replace it with `DefaultLocalAPIKey` during save.
- Non-loopback/public listeners with no auth are outside this task's behavior change; existing validation/warnings may continue to handle them.
- Provider and alias allow-lists must be validated on save. Unknown provider IDs or alias names are rejected by service APIs. Runtime filtering treats stale unknown IDs as invisible instead of widening access, and UI summaries should warn when stale config entries are detected.
- API key secrets must be unique across active collection entries and must not duplicate the legacy `server.api_key`. Create, update, and rotate reject collisions before saving.
- Once `apiKeys` is non-empty and legacy `server.api_key` is empty, delete/disable/update operations must not accidentally leave the proxy with no valid authentication path and fall back to no-auth. Blocking that state is required unless a future explicit no-auth confirmation flow is added.

### App Service

Expose app-level methods for GUI/web:

- list API keys with masked secrets and derived policy summaries
- create/update key policy
- rotate key secret
- delete key

Validation happens at service boundary before config save.

List responses must always return masked secrets. Create and rotate responses may return plaintext once so the UI can show a one-time copy surface; subsequent list/detail reads must not return plaintext.

Update APIs must not accept or overwrite the secret field. Secrets are written only by create and rotate operations. Requests that include a `key`, plaintext secret, or masked secret in a normal policy update should be rejected so editing a key cannot accidentally replace the stored secret with a mask string.

Key lifecycle APIs are administrative. Wails bridge calls are trusted like the existing desktop config UI. HTTP/browser fallback must use the existing admin authentication boundary and must not allow scoped proxy API keys to list, create, rotate, edit, or delete keys.

### Proxy

Authentication must resolve the presented bearer/API key to an enabled config entry. It must reject missing, unknown, disabled, or expired keys. Legacy single-key behavior may be preserved only if existing config requires compatibility.

Proxy auth decision matrix:

- `apiKeys` non-empty and legacy key absent: missing, unknown, disabled, or expired credentials are rejected.
- `apiKeys` non-empty and legacy key present: legacy key authenticates as unrestricted; otherwise credentials must match an enabled, unexpired collection key.
- `apiKeys` empty and legacy key present: keep current static-key auth behavior.
- `apiKeys` empty and explicit legacy key empty: keep current no-auth behavior.

Credential precedence must be deterministic. If both `Authorization: Bearer ...` and `X-Api-Key` are present and resolve to different raw values, reject the request. If both are present with the same raw value, authenticate once normally. Invalid primary and valid secondary credentials must not be accepted silently.

Proxy error semantics:

- Missing, unknown, disabled, expired, or conflicting credentials return `401` in the protocol's existing error envelope.
- Authenticated keys that request a hidden alias or a visible alias with no policy-visible targets return a model-not-found/policy-denied error without revealing hidden provider names.
- Future quota failures should use a quota-style client error before any upstream stream starts.

Model resolution rule: every request `model` is resolved through configured aliases first, then expanded into provider targets. The resolved key policy filters alias visibility and provider targets before routing. If no candidate remains, the proxy must fail before contacting upstream. Direct provider-native model routing is not introduced by this task.

Routing and `/models` must use the same resolved policy filtering rules. Alias lookup, model visibility, provider target expansion, and candidate selection must share one policy filter path so a hidden model cannot still be routed by direct request.

Token limits are enforced only if existing request trace usage data can provide a safe cumulative total without adding a new accounting store. If safe enforcement is not possible in this task, token limits are persisted and displayed as metadata only, and the UI/API must label them as not enforced yet. Future enforcement should return a quota-style error before starting upstream streaming; mid-stream cutoff is out of scope for this task.

### Frontend

Frontend uses typed API models matching app service views. It never receives or stores plaintext secrets except one-time create/rotate responses.

The header version must come from the same backend meta contract in Wails and HTTP mode. Packaged builds should use the linker-injected version; local builds may still return `dev` only when the actual runtime version is unset or intentionally built that way.

## Acceptance Criteria

1. GUI and browser web header display the effective runtime version, not hardcoded `dev`.
2. API Keys page is reachable from desktop and HTTP browser fallback UI.
3. Users can create, edit, disable/enable, rotate, and delete API keys.
4. New keys support never/fixed/relative expiration UX; relative days persist as an absolute expiration timestamp.
5. Expired keys are rejected by proxy auth.
6. Token limit metadata is persisted and surfaced; if enforcement is not safe with existing counters, UI/API clearly mark it as not enforced yet.
7. Price limit metadata/interface is present but clearly marked reserved/not enforced.
8. Provider and alias allow-lists persist and survive reload.
9. `/models` for a restricted key hides aliases outside alias scope and aliases with no visible provider target.
10. Proxy requests using restricted keys cannot route to disallowed providers or aliases.
11. All new UI strings have English and zh-CN locale entries.
12. Existing provider, alias, sync, and proxy workflows keep current behavior for unrestricted/admin keys.
13. Legacy `server.api_key` configs continue to work after upgrade.
14. Create/rotate returns plaintext key once; list/detail returns only masked key text.

- Frontend typecheck/build for new page and i18n keys.
